# Brief (Opus): embedding provider plugin for kb - public plugin surface, current approach as default

You are in the embedding-plugin worktree of the kb repo on branch feat/embedding-plugin. kb is Nick's knowledge-store CLI (Go). Nick's requirement, in his words: develop "a plugin approach where a embedding plug-in can be used by different projects because my work computer can't load hugging face models so I'd like an approach to work if someone added an api based embedding approach or their own local embedding model or whatever. Just have default be current approach as first user of plugin."

Where kb stands today (verify in code, do not take this on faith): internal/embed defines an Embedder interface (Embed/Model/Dim, optional Prefixer); internal/embed/provider builds one from flags/env with a hardcoded switch - ollama (the default; a local/remote Ollama server), openrouter and openai (both via the OpenAI-compatible client in internal/embed/openai), none (FTS-only), plus internal/embed/fake for tests. Vectors are stored at a fixed dim (768) and embed_meta refuses to mix embedders without a reindex. The limits of the current shape: everything lives under internal/ so no other project can import it, and adding a provider means editing kb's own switch.

Design and implement the plugin approach, scoped to kb's embedding layer:
1. A public, importable plugin surface (not under internal/) that defines the embedding provider contract and a registry/selection mechanism driven by configuration (name + options from env/flags/config), so another Go project could depend on it and register its own providers. Document how a different project uses it (README section or package docs in the new package).
2. kb refactored to consume that surface, with the CURRENT approach as the default provider and first user: with no new configuration, behavior is exactly today's (Ollama default, OpenRouter auto-selected when its key is set, openai, none; same env vars keep working, or any rename is additive/backward-compatible and documented). embed_meta's no-mixing guard must keep working.
3. Two more provider shapes, implemented with tests (stubs are acceptable where a real service is needed, but the provider itself must be real code, exercised against a fake server or fake command):
   (i) an API-based provider - generic HTTP embeddings API configured by base URL + API key + model (no vendor lock-in beyond an OpenAI-compatible request shape);
   (ii) a bring-your-own local model provider that does NOT load Hugging Face models in-process - e.g. a provider that talks to a user-run local server over HTTP, or an external-command provider that runs a user-supplied program and exchanges JSON. Pick the shape that best fits the codebase and justify it in the design doc/comments. Nothing in the design may require downloading or loading HF model weights in-process.
4. Tests: the existing suite must stay green (`go test ./...`), plus new tests proving provider selection by configuration and that switching providers works (including the external/local provider against its fake).
5. A short design note in the repo (docs/embedding-plugin.md or the package README) covering the interface, how providers register, how kb's default maps to today's behavior, and how a second project would adopt it.
