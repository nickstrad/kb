# Search latency and scale
> Each search = model load + query embed + FTS + vec0 KNN + log write; the KNN is brute force, so its cost grows linearly with chunk count.

- **Category:** resource/performance
- **Status:** watch
- **Where:** `internal/search/search.go` + `settings.go` (`search.Params` from config `[search]`: list_limit 20, vec_overfetch 60 for tag filters, rrf_k, weights; config caps list_limit/vec_overfetch at 4096 = sqlite-vec's max KNN k), sqlite-vec `vec0` (no ANN index; `internal/store/sqlite/retrieve.go` `knn`/`filterByTag`), `internal/store/sqlite/log.go` (`LogSearch`).
- **Why it matters:** agents search often; the latency adds up per task. Tag filters over-fetch and can miss results when a tag is rare. Cross-store search (Phase 3) multiplies the work.
- **Evidence:** about 0.2 s per search on a small corpus, mostly the model load. KNN cost on 10k+ chunks is unmeasured. `TestVecOverFetchBoundary` pins the 60/61 edge. W2 pass: hybrid and vec searches first check `sqlite_master` for `chunks_vec` (one indexed lookup) and skip the query embedding when it is missing, so an upgraded-but-not-reindexed store pays no model load.
- **W6 wave-end pass:** harness `search-settings` (H32) runs every [search] key at its max (list_limit/vec_overfetch 4096, candidate_limit 8192) on a tiny corpus: exits 0 with finite JSON; the cost at those sizes on a real corpus is still unmeasured. `kb stores` counts each store's entries by reading every entry row (`Entries`), linear in corpus size per store (Q58).
- **Coverage today:** boundary tables for ListLimit, CandidateLimit, PerEntryCap and vecOverFetch at their defaults and as config params (min, ±1, config max; `TestListLimitParamBoundary` pins vec0's 4096 cap); `FuzzFuse`/`FuzzApplyCap` properties; harness hostile queries.
- **Next checks:** a benchmark at 1k/10k/50k chunks (FTS vs KNN vs total) and the same with 1, 3 and 8 extra stores (the fan-out wall time should be the slowest store, not the sum); with list_limit/vec_overfetch user-settable up to 4096, measure KNN + ChunkMeta cost at that size; whether an `entry_tags` join (5.2) fixes rare-tag recall; whether binary/int8 quantized vec0 columns are worth it at scale.
- **W7 wave-end pass (4.1, 2.2, 1.5):** rendering (`cli.renderHits`) adds one indexed `st.Entry` lookup per distinct hit path (memoised per search), at most list_limit lookups; `--budget` trims after rendering, so it does not cut store work. `kb explain` re-runs retrieval with per-column bm25 and does not log. In-place sources (1.5) can grow chunk counts by whole repositories, which makes the KNN benchmark more urgent. `kb show`/`edit` paid a full source discovery per call (0.5–0.7 s at 10k files); fixed in the pass: Resolve walks lazily and reads one file (2k files: 59 → 4.3 ms, `BenchmarkResolve`). `kb stores` counts entries with `count(*)` (`sqlite.EntryCount`, Q58) instead of reading every row.
- **W8 (3.2) + wave-end pass:** cross-store search runs every store's search in its own goroutine (`search.fanOut`; at most `MaxExtraStores` = 8 extras), each with its own FTS + KNN and its own query embedding, memoised per (model, dim, prefixed text) by `search.QueryMemo`; the merge is O(total candidates) and cut to the primary's candidate_limit. Rendering now reads entry rows once per store (`EntriesByPath`, one `IN (...)` query of ≤ k paths), closing the batched-lookup next check. Each extra store is an extra read-only open (file handle, WAL read) per search. Fan-out cost on real corpora is unmeasured; the harness `stores-fanout` checks behaviour only. A panic in any store's worker is handed back to the command goroutine (`errs.WorkerPanic`, exit 3).
- **W9 (4.5, 4.2) + wave-end pass:** a query with an identifier field runs a third list, a second FTS5 MATCH over `chunks_exact` with the same AND→OR retry (so up to two more statements per search per store); its time is added to `fts_ms` (no separate column). `--expand section|entry` reads one entry's chunks per distinct hit entry (`Index.Chunks`, cached per search) through the hit's own store, before the budget cut, so expansion is at most k extra indexed reads. Both unmeasured at scale; the benchmark next check should include an identifier query and `--expand entry`.
- **W10 (5.5, 5.6, 4.3) + wave-end pass:** synonyms (5.5) add OR alternatives per expanded term to the FTS MATCH (at most 16 per term). Spell correction (5.6) runs only when the main FTS list returns fewer than 3 rows, and then reads the vocabulary twice: `DocFreq` (indexed `term IN (...)` lookups) and `VocabTerms`, a `GROUP BY` aggregate over the whole `chunks_exact_vocab` (every distinct identifier-index term, filtered by length and doc ≥ 2), so a no-hit search on a big corpus pays a vocabulary-sized scan plus a second FTS search for the correction. `kb synonyms suggest` reads judged searches and `DocFreq` only. `kb context` runs one search then reads each chosen entry's chunks. All unmeasured at scale; the benchmark next check should include a misspelled no-hit query on a 50k-chunk store.
- **W11 (5.3) + wave-end pass:** every search with `search.supersede_penalty` < 1 (default 0.5) makes one more read, `Retriever.Superseded` (an indexed `IN (...)` over the candidates' distinct entries, at most candidate_limit paths): 34 µs for 40 paths at 5k entries / 25k edges (`BenchmarkRelated/superseded40`); penalty 1 skips it. `--neighbors` runs one depth-1 `Related` per distinct primary-store hit entry (≤ k). As written in 5.3 the walk joined edges with `OR` and the final step read the whole edges table, 7.7 ms per call at 5k/25k (≈ 150 ms for a 20-hit `--neighbors` search, 26 ms for `kb related --depth 3`); the pass rewrote it as index lookups (src via the primary key, dst via `edges_dst`, candidate edges by rowid): 0.74 ms depth 1, 0.73 ms depth 2, 0.89 ms depth 3 (`BenchmarkRelated`, internal/store/sqlite/related_bench_test.go), checked against `RelatedModel` by FuzzRelated. Harness `links-stale` bounds `kb related --depth 3` on a 400-entry dense graph (≈ 35 ms wall, 1708 edges).
