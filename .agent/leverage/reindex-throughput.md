# Reindex throughput
> Indexing cost is dominated by embedding (~33 ms per chunk); reuse decides whether a reindex takes seconds or minutes.

- **Category:** resource/performance
- **Status:** watch
- **Where:** `internal/reindex` (batching, reuse by `text_hash` via `store.Index.Embeddings`), `internal/chunk` (chunk count and size), `internal/embed/cached.go` (machine-wide cache, wired in `cli/setup.go` `withEmbedCache` since 3.3b).
- **Why it matters:** migrations v3 and v7 force a reindex. Large in-place sources (1.5) multiply chunk counts. A slow reindex blocks agents and holds write locks.
- **Evidence:** about 33 s per 1,000 chunks at batch 16 (spike). Only titled docs chunks change on the 4.4 context-line change, so reuse limits the cost. W2 pass: `All` now runs a second Discover (which reads every front door) only when there are prune candidates, so a steady-state run pays nothing extra; a run that removes entries pays one more directory scan.
- **Coverage today:** `TestBatchSizeBoundary`, reuse tests in reindex; the cache acceptance test makes 0 model calls on the second embed.
- **Next checks:** a benchmark (`go test -bench`, model tag) for 1k/10k chunks cold, warm and cached; transaction granularity (one per entry vs batched) against concurrent readers; progress output and resumability after an interruption.
- **W7 (3.3b, 1.5):** the machine-wide cache is wired into every embedding command (`withEmbedCache`), so a second store or a re-created store reuses vectors by text; in-place sources (1.5) can multiply chunk counts by whole repositories. Still unmeasured.
- **W9 wave-end pass:** indexing adds one `chunks_exact` insert per chunk (a second tokenizer pass over the same text); negligible next to ~33 ms/chunk of embedding, unmeasured on FTS-only stores where it may be most of the non-embedding cost.
- **W10 (5.2) + wave-end pass:** every `All` and `One` (so every kb add, edit and `kb reindex <entry>`) ends with `ResolveEdges`, which reads every entry, every distinct chunk source file and every edge and runs the Go resolver: its cost grows with the corpus, not with the change. `BenchmarkResolveEdges` (internal/store/sqlite/edges_bench_test.go; 3 chunks and 5 edges per entry, M5 Max, FTS-only): steady state (nothing to update) 4.0 ms at 1k entries, 29 ms at 5k; resolving every edge from NULL 16 ms at 1k, 90 ms at 5k. It runs in a BEGIN IMMEDIATE transaction even when it writes nothing, so it holds the write lock that long. Negligible next to embedding today; at ~50k entries a single `kb add` would pay ~0.3 s. v7 clears every body_hash, so the first reindex after `kb migrate up` re-chunks everything (embeddings reused by text_hash).
- **Next checks (W10):** rerun the benchmark at 20k–50k entries; if steady state passes ~100 ms, resolve only edges whose target set could have changed (the entry's own edges plus edges naming its path, basename or aliases), or take the read in a deferred transaction and upgrade only when a row changes.
