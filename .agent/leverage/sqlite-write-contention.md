# SQLite write contention
> Several kb processes (agents, editors, a reindex) write one store at once; locking mistakes lose data or stall commands.

- **Category:** contention
- **Status:** validated (2026-10-30)
- **Where:** `internal/store/sqlite/sqlite.go` (DSN: WAL, `_busy_timeout=5000`, `_txlock=immediate`; `enableWAL` retry), `internal/store/sqlite/log.go` (a search log write on every search), `internal/reindex` (`All` discovers, then prunes), `internal/embed/cache`.
- **Why it matters:** many agents share one store, so concurrent add/search/reindex is the normal case. Before 0.5b, deferred transactions skipped the busy timeout and lost entries.
- **Evidence:** the adversarial harness `concurrent-fresh-db` found "database is locked" (fixed in 0.5b with IMMEDIATE transactions; knowledge: `sqlite-deferred-tx-locked.md`). The reindex-prune race (Q22: `reindex --all` deleted an entry a concurrent `kb add` committed after its Discover) is fixed in the W2 pass: `All` discovers again after `ListEntries` and prunes only rows neither discovery found (knowledge: `reindex-prune-rediscover.md`). `concurrent-fresh-db` then passed 7/7 runs (it failed about 1 in 3 before). W3 (1.2 moved the store to `internal/store/sqlite`): 7/7 passes again; a lock held past busy_timeout is now a Conflict ("stayed locked by another kb process; try again", exit 1), not an incident.
- **Coverage today:** `TestConcurrentWritersFromTwoHandles` (sqlite, `-race`); `TestEnableWALRetries` (fault driver: transient and permanent WAL failure); `TestWrapClassifies` (busy/locked → Conflict); `TestAllKeepsEntryAddedDuringRun` (reindex, deterministic: the embedder plays the concurrent add after Discover); harness `concurrent-fresh-db` (one shot per run; repeats are manual until H13); cache concurrency tests.
- **Next checks:** `-repeat N` for racy scenarios (H13) and a 20× run per wave; `kb add` vs `kb rm` of the same entry and `reindex --all` while a slow search holds a read transaction (H13); p95 search latency while a reindex runs (does the search-log write wait behind a long reindex transaction?); a fan-out search while an extra store is being reindexed or migrated (H44); the shared embedding cache across processes (H19).
- **W7 wave-end pass:** no change to the DSN or transaction mode. New writers: `kb migrate up` (serialised by the migrate flock; harness `migrate-concurrent`, 3 processes × 6 rounds), the v4 search-settings columns ride the existing one-row log insert. The shared embedding cache is now a real cross-process writer (see embedding-cache-shared-file).
- **W8 (3.2) + wave-end pass:** fan-out opens every extra store read-only and never writes it (`TestSearchFanOut` compares adr's bytes before and after); only the primary logs, one row set per search with the `store` column (v5). New log readers: `sqlite.Judged` (kb eval, read-only open). Verdicts and opens are now stamped with the caller's clock (Q81). Harness `stores-fanout`, `cache-two-stores` and `migrate-concurrent` passed 3/3 repeats each. Not yet probed: a fan-out search while another process reindexes or migrates one of the extra stores (H44).
