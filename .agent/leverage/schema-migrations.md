# Schema migrations
> Forward-only migrations of the store index DB carry the search log, the only irreplaceable data in a store; the lock, backup and apply sequence and the declared effects must be right.

- **Category:** data integrity
- **Status:** watch
- **Where:** `internal/migrate` (Steps, Run: flock on `migrate.lock`, backup `<file>.bak-v<N>-<ts>` via the artefact, apply, verify, prune to 3); adapters `internal/store/sqlite/artefact.go` + `migrations.go` (`index/0001..0003`, `Store.migrate` under BEGIN IMMEDIATE, `checkVersion`), `internal/embed/cache/artefact.go` (`cache/0001`); planned v4–v8 (docs/PLAN.md §2.5) and the config/location adapters (1.8b).
- **Why it matters:** a bad migration silently corrupts or drops history. Until 1.8b, any read-write open still migrates automatically (no backup, no flock), including an agent's `kb search`; old binaries refuse upgraded databases. From 1.8b the weakness moves to: the refusal path is clear, `kb migrate up` backs up under the lock, and declared effects match reality.
- **Evidence:** v2/v3 log-preservation tests (`TestMigration2KeepsSearchLog`, `migrate3_test.go`). 1.2 (W3): `sqlite.Open` is the only version check; a failed migration rolls back (`TestOpenFaults`). 1.8a (W6): a cancel during the **last** step still committed (pinned `*sql.Conn` and mattn run statements on an already-cancelled ctx); fixed with a `ctx.Err()` check before COMMIT (`TestApplyCancelledMidStep`; knowledge sqlite-cancel-surfaces-as-interrupt). A negative `user_version` used to reach the migration loop; now Conflict "damaged".
